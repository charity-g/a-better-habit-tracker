# README: Architecture & Plan

An offline-first, extensible, and backendless habit-tracking progressive web application designed with an ultra-lightweight frontend stack.

## Tech Stack Summary

| Concern | Choice | Why |
| --- | --- | --- |
| **Framework** | Preact + Vite | Ultra-tiny baseline bundle footprint (~40KB gzipped) and fast initialization. |
| **State Layer** | `@preact/signals` | Fine-grained reactivity. Components update individual DOM text nodes or attributes directly without executing component tree re-renders. |
| **Local DB** | IndexedDB via `idb-keyval` | 600-byte promise-based wrapper perfect for fast state hydration and offline data durability. |
| **Sync Protocol** | Background Sync API + Apps Script Web App | Complete data privacy with zero host infrastructure costs. No server required. |
| **PWA** | `vite-plugin-pwa` + Workbox | Caches static assets aggressively to serve the app immediately without connectivity. |

## Layered Architecture: Separation of Concerns

The codebase follows an strict, decoupled architecture pattern where the view layer, client orchestration, and persistent storage interact exclusively across defined bounds.

```
┌─────────────────────────────────────────┐
│                 UI Layer                │  ← Swappable View. Reads from signals.
│    (Preact Components, Theme, Layout)   │    Never calls storage or API directly.
├─────────────────────────────────────────┤
│            Facade Layer (API)           │  ← Public API Facade (habitStore)
│    (Context hooks, queries, actions)    │    Translates intent into store operations.
├─────────────────────────────────────────┤
│        State & Persistence Engine       │  ← Single Mutation Authority (applicationStore)
│   (Signals, local storage, API sync)    │    Mutates state arrays and updates local IDB.
├─────────────────────────────────────────┤
│              Network Pipes              │
│       Google Apps Script Web App        │  ← Appends transaction records to private
│           (REST via fetch)              │    Google Sheets spreadsheets via POST.
└─────────────────────────────────────────┘

```

### The Architectural Blueprint

* **`habitStore` (The Public Facade)**
Acts as a thin, descriptive API abstraction layer exposed to the Preact UI components. It performs query derivations (e.g., `getLogsForDate`) and forwards user requests directly to the core state processor.
* **`applicationStore` (The Single Mutation Authority)**
The core runtime engine of the application. It owns the internal `@preact/signals` wrappers, governs local storage mutations via `idb-keyval`, controls the state of network queues, and acts as the **only system module** authorized to change states.

## Strict Mutation Principles

To prevent race conditions, duplicated logic, and split-brain sync behavior across local and cloud environments, the code enforces an iron-clad state modification boundary:

### 1. Single Mutation Authority

Only `applicationStore` is permitted to write or append directly to the raw signal values (`habitsSignal.value` and `logsSignal.value`).

### 2. Forbidden Anti-Patterns

* **❌ Logic Duplication:** Do not build mutations that manually bypass the single engine authority. For example, `habitStore.markLogSynced` must never directly re-assign arrays; it must call `applicationStore.markLogSynced()`.
* **❌ Partial Re-implementations:** The facade layer must not run fractional mutations before forwarding.
```typescript
// ⛔ BAD PATTERN
habitStore.addHabit = (habit) => {
  habitsSignal.value = [...habitsSignal.value, habit]; // <-- Direct mutation breach!
  applicationStore.persistLocally();
};

```



### 3. Cascading Workflow Rule

Every data modification follows a strict, predictable chain reaction controlled completely by the application store:

$$\text{User Action} \longrightarrow \text{State Mutation} \longrightarrow \text{IndexedDB Flush} \longrightarrow \text{Background Cloud Sync Trigger}$$

## Offline-First Cloud Synchronization

The sync service prioritizes the integrity of local state data so users can track information smoothly on spotty mobile network connections.

```
       User logs habit via UI
                 │
                 ▼
     Append log locally to store
    (status: SyncStatus.Pending)
                 │
                 ▼
    Flush to IndexedDB instantly 
      & update UI via signals
                 │
                 ├─── Browser Online? ──Yes──► POST payload to Apps Script
                 │                                      │
                 │                               Response 200 OK?
                 │                                ├── Yes ──► Mark Log as SyncStatus.Synced
                 │                                └── No  ──► Mark Log as SyncStatus.Error
                 │
                 └─── Browser Offline? ──────► Wait for network connection event listeners
                                                        │
                                               Re-established connection ──► Trigger sync engine loop

```

### Critical Rules for the Sync Engine:

1. **Never Assume Delivery:** A record’s local status remains `SyncStatus.Pending` until an HTTP response code `200 OK` is successfully received and parsed.
2. **Network Interruption Resilience:** If an unhandled network error occurs or a fetch times out midway through processing a batch of items, the synchronization loop immediately issues a `break` command, keeping the remaining items safely in the local queue for a later sync attempt.
3. **No Database Dependencies:** Data tracking uses an atomic, append-only setup that pushes changes up to Google Sheets with sequential rows: `date | habitId | name | values | note | timestamp`.

## MVP Construction & Implementation Sequence

We will build out the core infrastructure in this specific logical order:

1. **Infrastructure Foundation**: Set up TypeScript model contracts, the `SyncStatus` enum, and basic configuration managers.
2. **Persistence State Core (`applicationStore`)**: Build out signals management, `idb-keyval` data hydration, and state-saving features.
3. **Synchronization Logic Engine**: Write the background fetch processor loops, connection monitors, and recovery features inside the store.
4. **API Facade Layout (`habitStore`)**: Build the descriptive lookup functions and input methods to wrap the core engine safely.
5. **UI Layer Wiring**: Integrate input elements directly to the signals framework for fast, non-rendering layout updates.
