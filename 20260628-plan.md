## Architecture: Separation of Concerns

Here's the layered model I'd use:

```
┌─────────────────────────────────────────┐
│              UI Layer                   │  ← Swappable. Only reads from store.
│   (React components, theme, layout)    │    Never calls storage or API directly.
├─────────────────────────────────────────┤
│           Store / State Layer           │  ← Single source of truth (Zustand)
│   (habits, logs, sync status, settings)│    UI subscribes. Actions call services.
├─────────────────────────────────────────┤
│           Service Layer                 │  ← Pure functions, no UI coupling
│   HabitService  │  SyncService         │    Easy to unit test
├──────────────────┼──────────────────────┤
│   Local Storage  │   Google Sheets API  │
│   (IndexedDB)    │   (REST via fetch)   │
└──────────────────┴──────────────────────┘
```

**Key principle:** Your React components never know Google Sheets exists. They call `logHabit(date, habitId)` on the store. The store calls `SyncService`. The SyncService decides local vs. remote.

## Data Model (extensible)

Design the schema to be habit-agnostic from day one:

```typescript
// Core types — these never change
type Habit = {
  id: string;           // uuid
  name: string;
  icon?: string;
  color?: string;
  archived: boolean;
  createdAt: string;    // ISO date
  valueLabels: [{"labelname": str, "value_type": one of "string" "number", if is number there is also a scale of min and max,and also the atrribute "max-meaning": string}]
};

type HabitLog = {
  id: string;
  habitId: string;
  date: string;         // YYYY-MM-DD — not datetime, date is the key unit
  values: [{"labelname"}] etc for valueLabels
  note?: string;
  syncStatus: 'pending' | 'synced' | 'error'; <-- make this a global enum>
  createdAt: string;
  syncedAt?: string;
};

type AppSettings = {
  googleSheetsApiKey: string;
  spreadsheetId: string;
  sheetName: string;
};
```

The `type` field on Habit means you can add `'mood'`, `'duration'`, or `'multiple_choice'` later without changing the log structure.

## Offline-First Sync Strategy

This is the most important part to get right:

```
User logs habit
      │
      ▼
Write to IndexedDB (status: 'pending')
      │
      ▼
Update UI immediately (optimistic)
      │
      ├─── Online? ──Yes──► POST to Google Sheets
      │                           │
      │                     Success? ──Yes──► Mark 'synced' in IndexedDB
      │                           │
      │                           No──────► Stay 'pending', retry later
      │
      └─── Offline? ──────► Service Worker queues sync event
                                  │
                            Back online ──► Background sync fires
```

Use **IndexedDB** (via `idb` library, ~1KB) rather than localStorage — it handles larger datasets and async properly.

Use the **Background Sync API** (`ServiceWorkerRegistration.sync`) so the browser retries automatically when connectivity returns, even if the tab is closed.

**Critical rule:** Only delete/update local records to `'synced'` inside the `.then()` of a confirmed successful API response. Never on send.

## Google Sheets as a Database

A few things to know up front:

**Auth without a backend is the hard part.** Google Sheets API v4 requires OAuth2 or an API key. API keys only work for **public** sheets. For private sheets (which you want), you need OAuth — but that normally requires a redirect URI and a backend.

**The practical solution for no-backend:** Use the **Google Apps Script Web App** pattern:
1. User creates a Google Sheet
2. They paste in a small Apps Script you provide (like 20 lines) that exposes a `doPost(e)` endpoint
3. They deploy it as a Web App ("anyone can access") and give you that URL
4. You POST JSON to that URL — no OAuth needed, no API key, no backend

This is actually the standard pattern for "Google Sheets as a DB with no backend." It's more reliable than fighting OAuth without a server.

The sheet becomes append-only logs: `date | habitId | habitName | value | note | timestamp`
